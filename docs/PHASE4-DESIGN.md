# Phase 4 Design — The Analysis Layer

Status: **proposal — awaiting review.** No file outside this document has
been touched. Per the Phase 1/2/3a/3b pattern, this is the check-in gate
before any analysis code, report, or non-doc file is written.

## Restating the committed record

### (a) What Phase 4 was scoped to be, in the existing docs

Every prior phase left a specific pointer at Phase 4, not a vague "measure
it later":

- **`docs/PHASE2-DESIGN.md`** (rug pull's `task_id` pair,
  `..._v1_baseline`/`..._v2_pulled`): named *why* distinct `task_id`s were
  chosen — "Phase 4 analysis will want to filter 'the pre-pull approval
  session' from 'the post-pull session' directly by `task_id` without
  needing to inspect hashes first." Phase 4 is where a human (or a report)
  reconstructs *which session is which* in a human-legible way.
- **`docs/WAZUH-NOTES.md`** constraint 3: cross-references
  `fs_read_makefile`/`git_show_head_commit` as a scope boundary "Phase 3
  doesn't have to rediscover" — implying Phase 4 is where that kind of
  boundary gets *reported*, not just avoided in rule text.
- **`docs/PHASE3A-DESIGN.md`**: every recall/FP number is already computed
  with "the correct denominator per rule, not one blanket number," already
  joins alerts back to `session_id`/`scenario_id`/`task_id` "so 'which
  record fired which rule' is a data join, not manual eyeballing," and
  states its own honesty boundary ("these are self-authored variants... not
  that the rule generalizes to independently-authored or adversarial
  phrasing") **inline, every time a number is reported** — this is the
  precedent Phase 4 inherits, not a new practice to invent.
- **`docs/PHASE3B-DESIGN.md`**: explicitly weaker "0 FP" framing (no
  legitimate-version-bump fixture exists) and the credential-exfil/rug-pull
  cross-scenario artifact — both **already written up in the phase doc
  itself**, but as one-off prose in a build-results section, not as part of
  a *standing, aggregate, re-run-able* report that covers all techniques
  together.

**Put together: Phase 4 is the layer that takes what 3a/3b already proved
piecemeal (each phase's own ad hoc `wazuh-logtest` batch run + a hand-parsed
table in that phase's design doc) and turns it into one committed,
reproducible artifact covering every technique at once** — not new
detection, not new attacks, not new rules. Every phase's validation script
so far (my own scratch `parse_logtest.py` in 3a/3b, never committed) was
disposable; Phase 4 is where that becomes a real, reusable tool with a
durable output, so the next phase (or a reviewer, or future-me) doesn't
re-derive "does 100103 still fire correctly" from scratch each time.

**Who reads it and what decision it supports**: this is a solo/small
research lab, not a SOC — there's no analyst triaging live incidents. The
reader is the project owner (and, per this project's citation rigor, a
plausible future reviewer of the work), and the decision it supports is
*"is the current rule set good enough to build on, and what specifically is
still weak"* — i.e., informs whether to add techniques, broaden the benign
corpus, or invest in adversarial-variant testing next. It is explicitly
**not** meant to support live incident response; nothing here needs to run
continuously or against the live stream.

### (b) The standing discipline this inherits

- **Evidence over assumption, verified in-tool, not argued from
  structure.** Every claim in 3a/3b that mattered was checked against the
  real engine (`wazuh-logtest`), not inferred from reading rule XML. I did
  the same before writing this doc — see "The join, verified against real
  alerts" below; none of that section is asserted from the design docs
  alone.
- **Honest caveats stated, not implied away.** 3a: self-authored variants
  prove plumbing, not adversarial robustness. 3b: "0 FP" is a narrower claim
  than 3a's for the same reason there's no benign fixture that exercises the
  actual distinguishing case. Both must survive into Phase 4's aggregate
  report **verbatim in force**, not smoothed into a single clean headline
  number.
- **Batch/measurement-first workflow, not live-pipeline mutation.** Every
  phase's recall/FP measurement ran via a *batch* `wazuh-logtest` pass over
  a frozen or canonical file, specifically to avoid growing the live
  `telemetry.jsonl` for a measurement exercise. Phase 4 inherits this
  directly — see "Where it lives + how it runs" below.
- **The real rule engine, not a Python stand-in.** 3a said it explicitly:
  "the claim rests on the real decoder/rule path, not just [a] one-off
  script." Phase 4's report must be generated by actually invoking
  `wazuh-logtest` against the committed `wazuh/local_rules.xml` — reimplementing
  rule-matching logic in Python would be exactly the kind of "argue from
  structure instead of verifying" this project has repeatedly rejected.

## 1. Deliverable

**Primary: one reproducible, committed detector-performance report** —
markdown, in the same style as every other doc in this project — covering
all three techniques (tool poisoning, credential exfil, rug pull) with
per-rule recall and per-rule-correct-denominator FP, generated by a
committed Python tool rather than hand-assembled.

**Secondary, same tool: per-session reconstruction as a supporting
capability, not the headline product.** A `--session <id>` (or
`--task-id <id>`) mode that prints one session's full record timeline
alongside which rule (if any) fired on it — useful for spot-checking a
specific row the report calls out (the same role 3a's own "near-boundary
demonstration table" played by hand). This is not built as a separate
deliverable; it's the same join logic the aggregate report already needs,
exposed as a second CLI mode.

**Reasoning for "report primary, reconstruction secondary" rather than the
reverse or an even split**: per (a) above, the actual open question at this
point in the project is "is the ruleset good enough, where is it weak" — an
aggregate, cross-technique view answers that; a per-session reconstruction
tool alone would require already knowing which session to look at. The
aggregate report is also what lets 3a's and 3b's already-written honesty
caveats finally live in one place instead of three separate phase docs a
reader has to cross-reference by hand.

**Who reads it / what it supports**: stated in (a) above — the project
owner, deciding what to build next; not an operational/live tool.

## 2. Inputs + the join

### The join, verified against real alerts, not the design docs alone

Pulled one real alert of each currently-live rule shape straight out of the
live manager's `alerts.json` before writing anything below:

| rule | `data.session_id` | `data.scenario_id` | `data.task_id` | `data.label` | rug-pull-specific fields |
|---|---|---|---|---|---|
| `100101` | present | present | present | present | — |
| `100102` | present | present | present | present | — |
| `100105` (representative of `100103`–`107`) | present | present | present | present | — |
| `100201` (rug-pull drift) | **absent** | present | present | present | `drift_session_id`, `baseline_first_seen_session_id` |

This confirms exactly what `docs/PHASE3B-DESIGN.md` already flagged by
design: `100201`'s alert `data` genuinely has no key named `session_id` at
all — by construction, per 3b's disjointness fix (see below) — while
`scenario_id`/`task_id`/`label` are present on **every** alert shape,
`100201` included. **A join written as `alert["data"]["session_id"]` would
`KeyError` (or, if written defensively with `.get()`, silently return `None`
and drop every rug-pull alert from any per-session reconstruction) —
exactly the kind of silent gap this project's own discipline exists to
catch before it ships, not after.**

**Why `100201` looks like this — restating the 3b reasoning so this doc
doesn't quietly re-litigate a settled fix**: `100200`/`100201` are new
top-level rules, proven disjoint from `100100` (and, after the Suricata
finding, from the *entire* shipped ruleset — `docs/WAZUH-NOTES.md`
constraint 8) specifically by giving the drift record's session-identifying
field a name (`drift_session_id`) that `100100`'s own field-presence
condition (`<field name="session_id">`) cannot match. That fix is a Wazuh
rule-engine concern — it has to hold at the point Wazuh's rule XML
evaluates the record. It says nothing about what Phase 4's own,
entirely-separate Python code is allowed to call the field once it reads
the alert back out.

**The reconciliation, entirely inside Phase 4, touching nothing upstream**:
a small normalization step, run once per alert, before any join happens:

```
if "session_id" in alert_data:
    primary_session_id = alert_data["session_id"]
    related_session_ids = []
elif "drift_session_id" in alert_data:
    primary_session_id = alert_data["drift_session_id"]
    related_session_ids = [alert_data["baseline_first_seen_session_id"]]
else:
    # unrecognized alert shape -- fail loudly, don't guess
    raise ValueError(...)
```

`primary_session_id` is what every per-session reconstruction and every
recall computation joins on. `related_session_ids` is not discarded — for a
rug-pull alert it's genuinely useful context (the earlier session that
established the baseline being violated), so it's carried as a secondary
field on the normalized record, not silently dropped for being
inconvenient. `scenario_id`/`task_id`/`label` are read directly the same way
for every alert shape (confirmed present on all four above), and used as a
cross-check: the joined session's own `scenario_id`/`task_id` (from
telemetry) must match what the alert itself carried, or that's a real
correlation bug worth surfacing, not silently trusting one source.

**This does not weaken the 3b disjointness fix** — that fix is a property
of the rule XML and the JSON stream Wazuh parses; it was never a property
of what Phase 4's own in-memory Python is permitted to name a variable.
Reconciling the field-name difference at the analysis layer costs nothing
at the rule-engine level and reintroduces no collision risk, since nothing
gets renamed back inside the actual JSON records Wazuh reads.

### Inputs, concretely

1. `data/benign_corpus_v2.jsonl` (4727 records, 541 sessions) — frozen,
   unchanged.
2. The canonical malicious slice of `telemetry.jsonl` (`label=malicious`,
   currently 890 records across the tool-poisoning + credential-exfil +
   rug-pull sessions built in Phase 2/3a/3b).
3. The canonical `rugpull_alerts.jsonl` (8 records, per 3b's build).
4. All three piped through a **fresh batch `wazuh-logtest` run** against
   the currently-installed `wazuh/local_rules.xml` (see "Where it lives"
   below) — the report's alert data comes from that fresh run, not from
   reading the live, ever-growing `alerts.json` directly.

**Why not read `alerts.json` directly**: confirmed by grepping it —
it also contains rule ids `1`, `2`, `502`, `591` (Wazuh's own internal
agent/system messages, unrelated noise) alongside the `mcp_detect` group's
alerts, and it accumulates across every restart and every ad hoc live test
this project has ever run (including, still present, 3a's own
`attack_credential_exfil_sandbox_bait_live_confirm` live-confirmation
alert). A report built from it would be neither reproducible (its contents
depend on this machine's entire session history) nor clean (it needs
`groups` filtering to exclude non-`mcp_detect` noise first). A fresh
`wazuh-logtest` batch pass over the three committed inputs above sidesteps
both problems.

## 3. Honest metrics

**The concrete rule**: every number in the report's tables must carry its
caveat in the same cell or the immediately adjacent column — not in a
separate prose paragraph a reader can skip past. If a caveat can't fit
inline, the number doesn't get a bare headline presentation at all; it gets
a footnote marker that's visually part of the number, not a wall of text
below three tables down. Concretely, every recall/FP entry renders as e.g.
`100% (12/12, self-authored)` / `0/1011 (content/path rules)` /
`0/4727 (no legitimate-update fixture exists — see note)`, not `100%` with
the asterisk's meaning three sections away.

**Caveats that must survive into this report, carried forward verbatim in
force, not diluted**:

1. **Recall is measured against self-authored variants.** Proves the
   harness/server plumbing reproduces the attack shape reliably across
   wording/identity variation; does **not** prove robustness against
   independently-authored or adversarial phrasing. Applies to `100101`,
   `100102`, `100103`–`107`. The `100103`–`107` key-name axis is the one
   partial exception already on record (an adversarial-shaped test of a
   *named* blind spot, not a variant designed to pass) — restated as such,
   not folded into the same bucket as the others.
2. **`100103`–`107`'s 100% recall is bounded to the 5 argument-key names
   tested, not literally exhaustive.** A 6th, unobserved key name would
   still slip through by the rule family's own construction (no
   wildcard-field-name primitive in Wazuh's DSL, per `docs/PHASE3A-DESIGN.md`).
   The report states recall as "100% of 5 tested key names," not "100%."
3. **Rug pull's "0 FP" is a structurally weaker claim than the content
   rules'.** 3a's rules: 0 FP means the benign corpus never contains that
   attack-shaped content, true regardless of how the benign fleet evolves.
   3b's rule: 0 FP means the frozen corpus's pinned versions never change,
   which was true by construction *before* the watcher ever ran a single
   record — no benign fixture exercises the actual thing the detector needs
   to distinguish (a legitimate version bump). The report states this
   difference explicitly next to the two numbers, not as a single "0 FP
   across all rules" headline that erases the distinction.
4. **The credential-exfil/rug-pull cross-scenario artifact** (3b's finding:
   4 of the 8 rug-pull-rule alerts are real drift detections attributed to
   `credential_exfil_via_read` sessions, an artifact of 3a's own variant
   harness, not a rug-pull instance) gets its own line in the rug-pull
   section: "4/4 true positives on the rug-pull scenario itself; 4
   additional correct detections attributed to an unrelated scenario, named
   in `docs/PHASE3B-DESIGN.md`" — not folded into an "8 total" headline that
   reads as rug-pull recall.
5. **Coverage is limited to the modeled attack shapes**, restated from each
   phase's own coverage map: HTML-comment-only tool poisoning (no Unicode/
   homoglyph obfuscation); credential exfil via file read with a
   `tool_arguments`-scoped exfil signal (no `result_summary`/`raw`-wide
   scan, per the Makefile-collision constraint); rug pull via hash drift
   only (no schema-poisoning or other rug-pull variants). `git_show`'s
   zero-benign-denominator gap (`docs/WAZUH-NOTES.md` constraint 1) is
   restated once in the coverage section, not per-rule.

**What the report does NOT do**: compute a single blended
"precision/recall/F1" number across all three techniques. The techniques'
denominators, caveat classes, and even what "false positive" means (content
match vs. baseline drift) are different enough that one blended number
would itself be a laundering step — it would look like the crisp metric
this project has been careful never to overclaim. Per-technique tables,
side by side, no forced aggregate.

## 4. Where it lives + how it runs

**Directory**: proposing a new top-level `lab/analysis/` directory (sibling to
`lab/attacks/`, `lab/baseline/`, `lab/corpus/`, `lab/proxy/`), matching the established
one-directory-per-concern pattern (`lab/baseline/` for the persistent-baseline
detector, `lab/analysis/` for the measurement/reporting layer). Flagging this
as one of the open questions below rather than assuming, same as `lab/baseline/`
was Q4 in the 3b proposal.

**Run mode: batch, over the frozen/canonical corpus, via a real
`wazuh-logtest` invocation — not the live stream.** Concretely:
`lab/analysis/report.py` (a) reads the three committed inputs listed above, (b)
pipes them through one `docker exec -i wazuh.manager wazuh-logtest` batch
call (parsing stderr for the final matched rule per line, the same
mechanism this session's own scratch `parse_logtest.py` used for 3b's
validation — now a committed, reusable tool instead of a throwaway script),
(c) applies the join/normalization above, (d) computes per-rule/per-scenario
recall and FP with correct denominators, (e) writes the markdown report.

**Why batch-over-frozen-corpus, not live**: this is the same reasoning 3a
and 3b both already used for their own validation, restated for Phase 4 —
reproducibility from committed code is the explicit goal here (your
instruction), and a live-stream mode would make the report's output depend
on whatever happens to be in the live `telemetry.jsonl`/`alerts.json` at
run time, which is neither reproducible nor stable across machines. The
tool still needs the Wazuh manager container **up** (it's genuinely
invoking `wazuh-logtest`, not reimplementing rule matching in Python — the
standing "real engine, not a stand-in" discipline applies here as much as
it did in 3a/3b), but it never mutates the live pipeline and never depends
on what's accumulated in `alerts.json` historically.

**Output**: a markdown report — proposing `docs/PHASE4-REPORT.md`, committed
and regenerated (not hand-edited) each time the tool runs, mirroring how
`data/benign_corpus_v2.jsonl` is a frozen, committed artifact. Flagging the
exact filename as an open question too, since it could equally live as
`lab/analysis/REPORT.md` if the report is considered part of that directory's
own concern rather than a `docs/` deliverable alongside the phase design
docs.
